## What was built

(iOS 16.0+, SwiftUI, arm64, bundle id `com.ksignnext.app`), ready to

## How it was built

Five builders worked in parallel (Core/Domain/Data; IPA/Mach-O/
Entitlements/Verification; Certificate/Provisioning/Signing/
Injection — this area's first builder failed on output truncation
and delivered nothing, so it was re-dispatched as two smaller
builders; Download/Sources/Installation; UI + tests). The coordinator
then integrated them (see below). All code is original; nothing was
copied from the GPL-3.0 reference clones and no key/asset was copied
from the reference IPA. No P12, certificate, password or private key
is in the project (verified by scan).

## Integration fixes (coordinator)

1. **Duplicate type definitions (10 found, all resolved).**
   Builders defined the same types in Domain/Core and in the engines.
   Canonical = Core/Domain. Unified the models as supersets
   (`AppMetadata`, `ImportedIPA`, `IPAInspectionReport` now carry the
   union of both sides' fields), expanded `IPAError` with the
   engine-only cases, added `pending` to `DownloadStatus`, deleted
   the engine copies of `IPAError`, `SigningError`, `AppMetadata`,
   `ImportedIPA`, `IPAInspectionReport`, `IPAEngineProtocol`,
   `IPAValidationReport` (Domain shape), `DownloadError`,
   `DownloadStatus`, and the whole `DownloadEngineProtocol` (unused).
   The remaining same-name hits (`CodingKeys`, nested `Source`) are
   nested types in different files — not conflicts.
2. **Protocol unification.** `IPAEngineProtocol` is now the engine's
   7-method set; `ImportIPAUseCase` was rewritten to it.
   `MachOEngine` gained a `MachOEngineProtocol` conformance
   extension (URL-based methods over its `MachOFile` API).
3. **DI wiring.** `DependencyContainer` now constructs the real
   engines by default (IPA, Mach-O, Certificate, Provisioning,
   Download, Signing with `UnavailableZsignBackend`). The signing
   certificate resolver reads the certificate repository; the
   provisioning resolver re-parses workspace `.mobileprovision`
   files. `ProvisioningEngine` was fixed to derive a stable id from
   the profile UUID so the same profile resolves to the same id at
   import and at signing.
4. **Project files created.** `SupportingFiles/Info.plist`,
   `SupportingFiles/KsignNext.entitlements`,
   `Tests/Info.plist` (all were missing). The generator now excludes
   Info.plist/entitlements from the Resources phase, adds the
   bridging-header + entitlements settings, and includes `.h` files.
5. **One corrupted line fixed** (a regex in the merge mangled an
   ArchiveEngine zip-bomb guard; hand-fixed and re-verified).

## What is NOT verified (needs macOS + Xcode)

- **Compilation.** Every file is hand-checked only. Highest-risk
  spots: `ArchiveEngine` `Compression` streaming API types,
  `InstallationServer` SwiftNIO async `EventLoopFuture.get()`,
  actor-extension conformance of `DownloadEngine` to
  `SourceDownloadEngine`, strict-concurrency (`complete`) issues
  around `@unchecked Sendable` classes, the Core Data model
  attributes vs the repositories' key paths, and the
  `SWIFT_OBJC_BRIDGING_HEADER` (the header declares C functions
  with no implementation linked yet — this is fine for Swift
  compilation only because no Swift code calls them; linking
  zsign will require the C++ target).
- **Tests have never run.** They assume `@testable import KsignNext`.
- **SPM versions are ranges** (upToNextMajor from 0.9.0 / 4.8.0 /
  2.0.0 / 3.0.0), not pinned exact versions — Xcode will resolve
  them; record the resolved versions after the first build.
- **Signing is honestly unavailable until zsign is linked**
  (`SigningError.zsignBackendUnavailable`). This is the single
  biggest remaining task: add claration/zsign as a build-time
  dependency and implement the four `ksignnext_zsign_*` C functions
  in `ZsignBridge.h` against it. Do not fake this step.
- **No AppIcon PNGs.** Supply real 1024×1024 artwork before release.
- **UI wiring gap.** The modules use local view models; they are not
  yet wired to `DependencyContainer`'s engines/use cases. The
  container, use cases and engines are ready; the wiring is a
  follow-up (Dashboard expiry data and Mach-O details in the UI
  currently show "none/not determined" until wired).
- **Signing config.** `ExportOptions.plist` has a placeholder
  profile name and the workflow needs `APPLE_TEAM_ID`. Until the
  user supplies real signing, CI archive/export fails on code
  signing (reported separately from test failures by design).
